# BAU Cabal Requests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A BAU agent can stop a session to ask the Cabal a question or for a review; Martin edits and approves (or comments and denies) it on the dashboard; approval runs the Cabal at once in an AWS Lambda reached through IAM Roles Anywhere, and the answers return to the ticket for the next session.

**Architecture:** The agent ends with a fenced JSON block and a `BAU_CABAL:` line. The runner posts a `[bau:cabal-request]` marker comment and labels the item `bau-cabal`, which every night pass skips. The API's approve route invokes the `bau-cabal` Lambda (in `nakomis/mcps`, packaging the `cabal` library) in a background thread, using an AWS profile whose `credential_process` is `aws_signing_helper` with Cere's Home CA certificate. The answers (or a denial) go back as a marker comment, the label comes off, and the feedback pass treats the unacknowledged response as feedback on the PR. The snapshot (schema 3), dashboard and BD-1 gain a Cabal queue.

**Tech Stack:** Python 3.12 / uv / pytest / ruff / FastAPI / boto3 (host); Vite + React + Tailwind 4 + Biome + Vitest (web); Python 3.12 Lambda + DynamoDB, CDK in TypeScript (`nakomis/mcps`); Ansible, nginx and Rust BD-1 (`nakomis/home-infra`).

**Spec:** `docs/superpowers/specs/2026-10-18-bau-cabal-design.md`, **including section 13** (amendments after BAU-21 merged; they win where they disagree with sections 1 to 12). Builds on `2026-10-18-bau-questions-design.md`. Plane: BAU-23.

**Repositories and branches:** `nakomis/bau` on `bau-23-cabal-requests` (Tasks 1 to 7 and 12); `nakomis/mcps` on `bau-23-cabal-lambda` (Tasks 8 and 9); `nakomis/home-infra` on `bau-23-cere-cabal` (Tasks 10 and 11). Each repo gets its own PR titled with `(BAU-23)`. The bau tasks use a fake Lambda client, so the three repos can proceed in parallel.

## Global Constraints

- Every Plane and GitHub write goes through `bau/plane.py` / `bau/github.py`, driven from `bau/runloop.py`, `bau/abandon.py`, `bau/sweep.py`, `bau/triage.py`, `bau/answers.py` or the new `bau/cabal.py`. Update the CLAUDE.md line that lists these.
- Policy lives in `config/bau.yaml`; tests build explicit `Limits(...)`, `Nudge(...)` and `CabalConfig(...)`. `tests/test_config.py`'s `MINIMAL` gains every new key.
- Label, exactly: `bau-cabal`. Pickup, feedback, ready, triage and the sweep all skip it.
- Markers, exactly (honoured only on comments authored by `bau@nakomis.com`, and only as the whole last non-empty line):
  - `[bau:cabal-request n=<n> data=<base64url JSON>]`, payload `{kind, prompt, summary, pr_url}`
  - `[bau:cabal-answers n=<n> data=<base64url JSON>]`, payload `{prompt_sent, edited, comment, answers: [{provider, response, cost_usd, error}], total_cost_usd, cost_incomplete}`
  - `[bau:cabal-denied n=<n> data=<base64url JSON>]`, payload `{comment}`
- Agent final message: a fenced ```` ```json ```` block `{"kind": "question"|"review", "prompt": "<text>"}`, then the last line `BAU_CABAL: <one-line summary>`. `BAU_TOO_BIG` wins if both appear.
- Limits: `cabal_prompt_max_chars: 30000`, `cabal_requests_per_ticket: 2` (counts every request, approved or denied).
- Nudge: cabal warn at 3 or any older than 2 days; down at 6 or any older than 5 days.
- Denial text when Martin leaves no comment: `Martin declined; use your own judgement`.
- Success notice on the dashboard: `<REF>: Cabal answered (£0.21)`; an incomplete cost reads `at least £0.21`.
- Lambda: function `bau-cabal`, `eu-west-2`, Python 3.12, timeout 10 minutes, invoked directly with `lambda:InvokeFunction` (no API Gateway). Request id `<ref>#<n>`. Results kept 30 days. CloudWatch never receives prompt or answer text.
- The host's boto3 Lambda client has `retries={"max_attempts": 0}` and a read timeout above the Lambda timeout (`call_timeout_seconds: 660`): a botocore retry would be a second paid call.
- Provider keys: `/cabal-mcp/<name>` in the prod account only; never on Cere or in the agent container. No static AWS key on Cere.
- Roles Anywhere: reuse the existing `home-ca-prod` trust anchor (ARN from SSM `/conversation-memory/prod/trust-anchor-arn`), role trust pinned to `CN=cere`, permission `lambda:InvokeFunction` on `bau-cabal` only. ARNs published under `/bau/cabal/`.
- British English; commits carry `(BAU-23)`; no attribution lines.
- bau: `uv run pytest` (coverage ≥ 70%) and `uv run ruff check .` pass after every task; web tasks also `pnpm -C web test` and `pnpm -C web lint`.

## Review Focus

1. **An API restart, or a second click, mid-call** must never pay twice: the Lambda's claim returns `in_progress` for a live claim and the stored result for a finished one; the host never retries an invoke. Tests in Tasks 4, 5 and 8.
2. **Martin approves while the night is running**: approve and deny succeed (no run lock), and the night never touches the item while it is labelled. Tests in Tasks 3 and 5.
3. **A mid-ticket draft PR is marked ready** by `ready_pass` while the request is pending, or straight after the answers arrive before any session has read them. Test in Task 3.
4. **The answers arrive but the Plane write fails**: the label stays, the card shows the error, and approving again posts the stored answers at no extra cost. Test in Task 5.
5. **Large answers**: seven providers at their 4,096-token default give a comment of a few hundred kilobytes; it must round-trip through Plane's HTML and parse. Test in Task 1.

**Files:**

**Interfaces:**
- Consumes: Task 1's markers and `DENIED_DEFAULT`; Task 4's `CabalLambda`, `CabalResult`, `CabalInProgress`, `CabalFailed`, `CabalConfig`; `answers.clean_answer`, `answers._check_ref`.
- Produces:
  - `bau/cabal.py`: `class CabalBusy(RuntimeError)`, `class StaleRequest(RuntimeError)`, `class BadRequest(ValueError)`; `class Approvals(*, plane, client: CabalLambda, projects, worker_email: str, cabal: CabalConfig, limits: Limits, executor: concurrent.futures.Executor, on_settled: Callable[[str], None])` with:
    - `approve(ref: str, n: int, prompt: str, comment: str) -> None`: synchronous checks under a per-ref `threading.Lock`: valid ref and project; not in flight (`CabalBusy`); item carries `bau-cabal` and the latest request is `n` (`StaleRequest`); prompt non-empty and at most `cabal_prompt_max_chars` after `\r\n` normalisation (`BadRequest`). It then marks the ref `asking` and submits the job. The prompt is sent exactly as Martin left it; only his comment goes through `clean_answer`. `system` is `cabal.review_system_prompt` for `kind == "review"`, else None.
    - The job: `client.ask(f"{ref}#{n}", ...)`; on success, convert each `ProviderAnswer` to a `CabalAnswer` and post `cabal_answers_comment(...)`, then remove `bau-cabal`, then state `answered` with `cost_gbp`, then `on_settled(ref)`. Errors set state `failed` with fixed, token-free text: `CabalInProgress` → `"a previous call for this request is still running; approve again in a few minutes"`; a Plane failure after a result → `"the answers arrived but could not be posted to Plane; approve again to post them (no extra cost)"`; anything else → `"the Cabal call failed (<ExceptionType>)"`.
